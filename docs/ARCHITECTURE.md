# Trinity AI — Architecture (consolidated)

`API -> structured request -> job manager -> engine registry -> engine -> validation -> artifact manager -> SQLite lineage`

- LLM-independent: models emit structured tool-calls only, never execute engines.
- Deterministic engines (Python): `math` (SymPy) and `cad` (native mesh + STL/GLB) run locally. `pcb`, `firmware`, `simulation`, `robotics`, `vision` and `research` have real Python fallbacks (no status label): pcb places/routes/design-checks boards, firmware validates pins against an MCU database and labels builds `COMPILED` only after a real toolchain run, simulation/robotics solve their advertised ops, and vision/research run behind their optional extras. The native bridge is preferred whenever `TRINITY_NATIVE_EXEC` points at a built `Trinity.exe` (`src/engines/native_bridge.py`: one JSON `EngineRequest` on stdin, one envelope on stdout via `Trinity.exe --exec`; single-shot ops only, unmapped ops keep 501ing). New engine development lands in the native app, which owns the full roster (see `app/native/README.md`); Python owns the API, jobs, artifacts, and the bridge.
- CAD output formats are capability, not constant. `stl`/`glb`/`json` are pure Python and always available. `step` needs an optional CAD kernel (`pip install cadquery` → OpenCascade) and is resolved per call via `src/engines/cad/step.py`, so the catalog can report it unavailable with a reason and an export can name what it could not write. The kernel lift is one-way and faceted: the single mesh becomes planar faces sewn into one solid per connected body, giving AP214 geometry with no second set of builders to drift.
- Every call returns `{success, engine, operation, result, artifacts, validation, errors, job_id}`. Tracked failures are HTTP 200 `success:false`; unknown engine/job/artifact are real 404s.
- Accounts, billing, trust and limits are layered on the same app: JWT sessions and scrypt passwords (`src/api/accounts.py`), config-driven plans with HMAC-signed deduped webhooks (`src/api/billing.py`), four draft policy pages (`src/api/trust.py`), and per-day metering with honest 402s (`src/api/limits.py`). They are mounted after the engine router and do not change engine semantics.
- Frontend lives in `frontend/` (Next.js). Python core lives in `src/`. Runtime state lives in `data/` (gitignored except `.gitkeep`).
- Native foundation lives in `app/native/` (C++20 / CMake / Qt 6 / MSVC, `Trinity.exe`): same pipeline stages as native bootstrap (config → logging → paths → SQLite → engine registry → null model provider → Qt window) with all eight real engines shipped (math, cad, pcb, firmware, vision, simulation, research, robotics); see `app/native/README.md`.
